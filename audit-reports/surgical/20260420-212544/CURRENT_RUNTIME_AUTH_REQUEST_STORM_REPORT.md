## Executive Summary

The current runtime failure is a systemic bootstrap problem, not a single endpoint bug.

The frontend currently mixes three concerns inside the application shell:

1. session restoration
2. full inventory bootstrap
3. route-level permission/render decisions

That coupling causes repeated application-wide reloads after login. The reloads repeatedly hit the same six backend endpoints in near-lockstep. Once the request volume crosses the backend global rate limiter threshold, the backend starts returning 429 responses. From the user perspective, this looks like a broken login flow, unstable session state, and repeated permission guard messages.

The repeated Permission Guard console logs are real, but they are a symptom of repeated rerenders, not the primary failure. The actual production risk is the request storm plus an inconsistent authentication model in the frontend, plus a dangerous wildcard-permission fallback.

## Primary Findings

### Critical 1: Auth bootstrap is coupled to mutable store state

Evidence:

- `frontend/src/App.tsx:221` keeps the auth initialization effect dependent on `users`.
- `frontend/src/App.tsx:149` defines `initializeAuth` in that effect.

Why this matters:

- `users` is not stable session state.
- The inventory store reload updates `users`.
- Updating `users` can retrigger auth bootstrap behavior.
- This breaks Separation of Concerns and makes session initialization non-idempotent.

Architectural issue:

- The application shell is acting as both authentication bootstrap coordinator and domain data bootstrap coordinator.
- In a clean modular monolith, session restoration must not depend on mutable domain collections.

### Critical 2: Full application reload is triggered from multiple places

Evidence:

- `frontend/src/App.tsx:244` calls `useInventoryStore.getState().loadAll()` after login.
- `frontend/src/pages/Dashboard.tsx:32` calls `loadAll()`.
- `frontend/src/pages/Items.tsx:93` calls `loadAll()`.
- `frontend/src/pages/Operations.tsx:45` calls `loadAll()`.
- `frontend/src/pages/Reports.tsx:30` calls `loadAll()`.

Why this matters:

- `loadAll()` is application-wide synchronization, not module-local refresh.
- Multiple route mounts can trigger the same heavy bootstrap repeatedly.
- That produces the exact route-count pattern observed in runtime metrics.

Architectural issue:

- Route components should not own global application bootstrap.
- Page mount should request only the data slice needed by that page, or consume already bootstrapped state.

### High 1: Permission Guard logging is executed inside render path

Evidence:

- `frontend/src/App.tsx:606`
- `frontend/src/App.tsx:607`
- `frontend/src/App.tsx:612`
- `frontend/src/App.tsx:617`

Why this matters:

- Every rerender prints the same access-granted messages for every protected route.
- This creates misleading noise and hides the real performance issue.
- It also confirms that route-protection logic is being re-executed excessively.

Operational conclusion:

- The console spam is not the root cause, but it is valid evidence that the render cycle is unhealthy.

### High 2: Frontend session model is internally inconsistent

Evidence:

- `frontend/src/hooks/useSession.ts:15` returns `token: ''` unconditionally.
- `frontend/src/hooks/usePermissions.ts:138` derives `isAuthenticated` from `Boolean(session?.token)`.

Why this matters:

- The app currently uses cookie-backed auth behavior, but the permission hook still expects a token in local state.
- This means part of the app thinks the user is authenticated while another part can conclude the opposite.
- The issue is partially masked for SuperAdmin flows, but it is a real correctness defect.

Architectural issue:

- There is no single source of truth for authenticated session state.
- That violates clean application-state boundaries.

### High 3: Wildcard permissions are granted by faulty fallback logic

Evidence:

- `frontend/src/App.tsx:467`

Current behavior:

```ts
permissions: user?.permissions && user?.permissions?.length > 0
  ? user.permissions
  : (user?.role === 'SuperAdmin' || user?.role === 'admin' ? ['*'] : ['*'])
```

Why this matters:

- The fallback returns `['*']` for both admin and non-admin paths.
- That is a latent privilege-escalation defect.
- It also makes debugging permission behavior much harder because missing permission data is silently converted into universal access.

### High 4: Backend rate limiting amplifies the frontend storm instead of containing it safely

Evidence:

- `backend/src/security/global-rate-limit.ts:26` sets `max: 100`.
- `backend/src/security/global-rate-limit.ts:30` currently skips preflight and reset-attempts only.

Why this matters:

- After the frontend enters a request storm, the backend global limiter starts rejecting core bootstrap traffic.
- The user then sees a mixture of 429 and 401 responses.
- This turns an application orchestration bug into an apparent login failure.

Important note:

- Increasing the limiter alone is not a real fix.
- The request storm must be eliminated first.

### Medium 1: Read-only users and roles endpoints write audit records on hot path

Evidence:

- `backend/src/users/users.service.ts:113`
- `backend/src/users/users.service.ts:120`
- `backend/src/users/users.service.ts:131`
- `backend/src/users/users.service.ts:138`

Why this matters:

- `listUsers()` and `listRoles()` write audit records even for read/list traffic.
- Under a request storm, this adds unnecessary database writes.
- This increases pressure on the persistence layer and makes recovery slower.

Architectural issue:

- Cross-cutting audit should be applied selectively.
- High-frequency read paths should not generate heavy audit writes unless there is a clear compliance requirement.

### Medium 2: Application shell is overloaded with orchestration responsibilities

Evidence:

- `frontend/src/App.tsx` currently handles session restoration, route protection, inventory bootstrap, user synchronization, audit loading, and various domain-level side effects.

Why this matters:

- This is a classic application-shell overload smell.
- It reduces testability, increases rerender coupling, and makes root-cause analysis harder.

### Medium 3: Realtime and offline layers are not the primary cause, but they are extra moving parts in an already unstable bootstrap

Evidence:

- `frontend/src/services/realtimeSync.ts`
- `frontend/src/hooks/useOfflineSync.ts`

Why this matters:

- These layers are not the main cause of the request storm.
- However, they add connection and reconnection behavior during startup.
- They should be initialized after the session and critical bootstrap path are stable.

## Why the Current Console Logs Repeat

The repeated browser logs such as:

```text
[Permission Guard] SuperAdmin access granted to items
[Permission Guard] SuperAdmin access granted to dashboard
[Permission Guard] SuperAdmin access granted to reports
```

do not mean that the backend RBAC guard is looping.

They come from the frontend render path. Each rerender traverses the protected route tree again, and the logs run again. Because the app is also reloading global state repeatedly, those rerenders become very frequent. Therefore:

- the logs are real
- the logs are not the primary defect
- the logs are a strong symptom of a bootstrap/render loop

## Architectural Assessment Against Current System Principles

The repository instructions define the system around:

- Separation of Concerns
- Modular Monolith
- Clean Architecture

The current runtime path violates those principles in the following way:

1. Presentation layer owns application bootstrap decisions that should be isolated.
2. Route pages trigger global synchronization instead of requesting module-scoped data.
3. Session restoration depends on domain state (`users`) instead of a stable auth boundary.
4. Cross-cutting audit concerns are embedded in hot read paths.
5. Security fallback logic grants wildcard permissions when permission state is incomplete.

## Final Professional Solution

The final solution should not be a one-line patch. It should be implemented as a staged architecture correction.

### Phase 1: Immediate Stabilization

Objective: stop the request storm and restore predictable login behavior.

Required changes:

1. Remove `users` from the auth initialization effect dependencies in `frontend/src/App.tsx`.
2. Ensure auth bootstrap runs exactly once per session restoration event, not per store mutation.
3. Keep post-login bootstrap in one place only.
4. Remove page-mount `loadAll()` calls from dashboard, items, operations, and reports.
5. Keep manual refresh actions, but do not run full bootstrap automatically on every page mount.
6. Remove or dev-gate Permission Guard logs from render path.

Expected outcome:

- login becomes stable
- route tree stops rerendering excessively
- backend no longer receives synchronized storm traffic

### Phase 2: Correct the Authentication State Model

Objective: establish one source of truth for authenticated session state.

Required changes:

1. Replace the current empty-token session model in `frontend/src/hooks/useSession.ts`.
2. Make `usePermissions` derive authentication from the real session source used by the app.
3. If auth is cookie-based, expose a `sessionReady` and `sessionUser` model rather than a fake token requirement.
4. Align all protected-route logic with that single session contract.

Expected outcome:

- no split-brain auth state between current user, local storage, and permission hook
- correct behavior for non-SuperAdmin users

### Phase 3: Remove the Wildcard Permission Fallback Defect

Objective: restore secure permission semantics.

Required changes:

1. Fix `frontend/src/App.tsx:467` so non-admin fallback is `[]`, not `['*']`.
2. Treat missing permissions as an error or an explicit empty-permission state.
3. Prefer server-sourced permissions over synthesized fallback permissions except for well-defined emergency bootstrap cases.

Expected outcome:

- no accidental universal access
- easier debugging of RBAC problems

### Phase 4: Rebuild Bootstrap Around an Application-Orchestration Boundary

Objective: align the startup flow with modular-monolith architecture.

Recommended target design:

1. `App.tsx` should become thin and mostly responsible for route composition and high-level shell state.
2. Introduce a dedicated application bootstrap hook or service, for example `useAppBootstrap()` or `useAuthBootstrap()`.
3. That bootstrap unit should do only:
   - session restore
   - authenticated bootstrap trigger
   - bootstrap status reporting
4. Domain state loading should then be split into explicit module-level actions.

Preferred implementation model:

- Option A: one dedicated backend bootstrap endpoint such as `/api/app/bootstrap` returning the minimum startup bundle.
- Option B: a frontend bootstrap orchestrator that calls existing endpoints once and caches results safely.

For the current architecture, Option A is the more professional end-state because it:

- reduces client round-trips
- makes startup deterministic
- gives the modular monolith one application-level composition boundary

### Phase 5: Replace `loadAll()` as a Global Default Operation

Objective: make data loading intentional and bounded.

Recommended direction:

1. Split `loadAll()` into domain-specific loaders.
2. Use only the required loader per route.
3. Reserve full reload for explicit maintenance/refresh operations.
4. Add stale checks so a mounted page does not refetch already-fresh data.

Suggested target loaders:

- `loadInventoryCore()`
- `loadTransactions()`
- `loadUsersAndRoles()`
- `loadOpeningBalances(year)`
- `loadFormulations()`

### Phase 6: Make Backend Protection Layer More Intentional

Objective: keep backend protection strong without turning orchestration mistakes into cascading failures.

Required changes after frontend stabilization:

1. Keep a strict limiter for `POST /auth/login`.
2. Use a different limiter policy for authenticated bootstrap/read endpoints.
3. Avoid one global limit policy for all traffic classes.
4. Consider circuit-breaking or temporary deduplication for repeated bootstrap calls from the same session.

Important constraint:

- Do not treat backend limiter tuning as the primary fix.
- It is secondary containment only.

### Phase 7: Reduce Audit Load on High-Frequency Read Paths

Objective: keep audit meaningful and sustainable.

Required changes:

1. Remove audit writes for ordinary list/read traffic such as users list and roles list, unless a compliance requirement explicitly demands them.
2. If observability is needed, use sampled telemetry or metrics instead of persistent audit writes.
3. Keep full audit for mutations, authentication events, and security-significant actions.

## Recommended Implementation Order

1. Stop repeated auth/bootstrap triggers in `frontend/src/App.tsx`.
2. Remove page-level automatic `loadAll()` calls.
3. Fix session model inconsistency in `useSession` and `usePermissions`.
4. Fix wildcard permission fallback.
5. Remove render-path permission logs.
6. Reduce audit writes on hot read endpoints.
7. Refactor toward dedicated bootstrap orchestration.
8. Re-tune backend rate limiting once storm traffic is gone.

## What Must Not Be Done

1. Do not only increase the rate-limit threshold.
2. Do not only suppress console logs.
3. Do not add retries around `loadAll()`.
4. Do not keep `users` as an auth-bootstrap dependency.
5. Do not keep `['*']` as the fallback for non-admin users.

## Acceptance Criteria For Final Fix

The issue should be considered fully solved only when all of the following are true:

1. Fresh login produces stable navigation without 429 responses.
2. The first authenticated screen loads without repeated global reload cycles.
3. `Permission Guard` console spam is gone or explicitly dev-gated and deduplicated.
4. Non-admin users do not receive wildcard permissions implicitly.
5. `useSession` and `usePermissions` agree on the authenticated state.
6. Backend metrics show bounded route counts after login.
7. Users/roles read endpoints no longer generate avoidable audit-write pressure.
